# Maintenance standards

## Outline

1. Metadata and documentation by file type.
2. Source layout and configuration rules.
3. Immutable evidence and review boundaries.
4. Validation before a review request.

## File conventions

The default maintainer `sunshine-engineer` was explicitly supplied by the user for this maintenance task. It identifies the maintenance contact, not an invented original author. A `Modified` date records this file's maintenance edit, not when its functionality was implemented or tested.

| File type | Convention |
| --- | --- |
| Python | Comment header with repository-relative filename, maintainer and ISO modified date; module docstring explains purpose. Classes and every defined callable, including private/nested helpers and test fixtures, have a docstring. Document arguments, meaningful results and relevant failures. Simple test cases may use one sentence plus fixture arguments. |
| Shell | Keep shebang first, then comment metadata. Document helper inputs, output/side effects and failure status in comments; retain strict-mode settings. |
| YAML, TOML, INI, Dockerfile, Caddyfile, systemd and ignore/editor rules | Use native comment syntax without changing parser-visible keys or directive order. |
| JavaScript, CSS, HTML | Use native block comments. Keep accessibility and reader behavior covered by browser checks. |
| Maintained Markdown | HTML metadata comment before the title; headings and fenced examples remain Markdown. |
| JSON | No comments or invented schema keys. Metadata/purpose is recorded in the [file inventory](maintenance/file-inventory.json), not inserted into manifests, fixtures or reports. |
| Alembic Mako template | Use a non-emitting template comment for template metadata, preserving generated module content and revision metadata. |
| Generated locks and exact requirements | Preserve tool-generated bytes and exact pins; refresh with the relevant tool when dependencies intentionally change. |
| Approved content, review snapshots, historical evidence and third-party licenses | Preserve recorded bytes, dates and attribution. Existing manifests/reports retain their historical metadata; the inventory explains their exemption from new headers. |

The [tracked file inventory](maintenance/file-inventory.json) assigns every tracked file a purpose and policy. It deliberately excludes local secrets, ignored runtime output and untracked personal notes. `scripts.check_repository_consistency` checks missing headers/docstrings, strict JSON and stale inventory. Black, Ruff and MyPy handle Python formatting, import organization and type checking. `.editorconfig` supplies editor defaults; use existing format rather than reflowing frozen documents.

## Python organization

Use module metadata/docstring, future imports, standard-library/third-party/local imports, constants, logically ordered definitions, then the `__main__` entry point. Keep imports local when they isolate optional providers, prevent cycles or support disposable version probes. Preserve decorator order and runtime schema/tool descriptions; those can be executable contracts rather than cosmetic text.

Docstrings describe actual behavior: placeholder adapters say they return state unchanged. Do not claim generation, verification or sandboxing that the function does not perform. Keep usage examples focused on non-obvious boundaries; configuration examples and the README show normal commands, while recipe pages mirror their Python sources exactly.

For every configuration change, update [the configuration reference](configuration.md), the appropriate example file and any Compose consumer. Explicit arguments take precedence over deployment defaults. Credentials remain outside Git. Fixed schema versions, trusted source namespaces, prompts and exact test fixtures stay in code or immutable inputs where their value defines behavior or provenance.

The directory map is checked against actual modules. Reserved `prompts/`, `notebooks/` and empty legacy adapters are documented rather than moved or deleted, preserving their import paths. No structural move was justified by this audit.

## Evidence and approvals

Adding Pydantic class docs normally changes generated JSON-schema descriptions. Generation contracts explicitly omit class documentation from the established writer wire schema; a golden-schema/hash regression test prevents documentation-only changes from invalidating existing queued jobs. Field constraints and existing validation remain intact. Intentional prompt/schema changes require a reviewed prompt-version and golden-fixture update; do not bypass that guard to make a formatting change pass.

The four unapproved learning recipes receive matching snippet updates and a **new** execution report after documentation changes. The old report remains historical. Pending review entries are rebound to the changed page hashes and remain pending; neither this audit nor an execution pass grants content approval. Existing `@tool` docstrings remain concise because their literal text is runtime tool metadata; simple integer operands/results are also explicit in their signatures and examples.

## Before opening a PR

```bash
uv sync --all-groups --frozen
uv run black --check .
uv run ruff check .
uv run mypy .
uv run python -m scripts.check_repository_consistency
uv run pytest -m 'not db_integration and not real_model' -q
uv run --group site python -m scripts.build_docs_site
uv run playwright install --with-deps chromium
uv run python -m scripts.check_docs_site_browser
bash -n .devcontainer/setup.sh deploy/init-vm.sh deploy/ops.sh deploy/setup-vm.sh
```

Stage intentional new paths before refreshing the inventory:
`uv run python -m scripts.check_repository_consistency --write-inventory`.
Then review the diff and rerun the checker. Never stage local secrets or personal files just to make the inventory include them.

Also run PostgreSQL/model-marked tests against a disposable migrated database, exact-dependency teaching recipes, all compatibility probes and `python -m scripts.check_vm_deployment --build`. The [CI workflow](../.github/workflows/ci.yml) contains the isolated commands; the [README](../README.md) explains prerequisites. Record failures, skips and unavailable external services honestly. Container smoke tests do not establish actual VM/systemd/TLS behavior or real-provider quality.
