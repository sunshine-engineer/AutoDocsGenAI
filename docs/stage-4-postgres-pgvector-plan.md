# Stage 4 implementation plan: PostgreSQL and pgvector foundation

Status: migration applied; MVP lineage persistence and idempotent chunk import
implemented. Repository hardening is deferred to optimization.

## Objective

Create a reproducible, migration-managed PostgreSQL/pgvector persistence layer
and import the existing package, source, document, and chunk lineage
idempotently. Embedding generation is explicitly deferred to Stage 5.

## Stage boundary

Inputs:

- package name and requested version;
- confirmed official sources and crawl metadata;
- normalized `CleanDocument` records;
- deterministic chunks from `chunks.jsonl` or `PipelineState.chunks`;
- pipeline configuration snapshot.

Outputs:

- healthy Dockerized PostgreSQL with the vector extension enabled;
- version-controlled database schema;
- typed repository layer with explicit transactions;
- persisted run, source, document-revision, and chunk lineage;
- integration tests proving migrations and idempotent ingestion;
- documented start, stop, reset, backup, and restore commands.

Stage 4 will not call Ollama, generate embeddings, create an HNSW index, perform
semantic retrieval, or invoke agents.

## Technical decisions

1. Use a pinned `pgvector/pgvector` PostgreSQL image, not `latest`.
2. Run PostgreSQL as a Docker Compose service with a named persistent volume.
3. Use SQLAlchemy 2.x for typed database access and Alembic for schema
   migrations.
4. Use Psycopg 3 as the PostgreSQL driver.
5. Keep domain Pydantic models separate from SQLAlchemy persistence models.
6. Put transaction control in a unit-of-work boundary; repositories do not
   commit independently.
7. Use UUID primary keys for revisioned records and retain deterministic text
   chunk IDs as unique domain identifiers.
8. Store all timestamps as UTC `timestamptz` values generated by PostgreSQL.
9. Store heading paths and flexible fetch metadata as `jsonb` where their shape
   is naturally nested; keep frequently filtered values in typed columns.
10. Create the `vector` extension now but defer the embedding column and vector
    similarity index to the Stage 5 migration, after model dimension is frozen.

## Initial schema

### `packages`

Stable package identity.

- `id uuid primary key`
- `name text not null`
- `ecosystem text not null default 'pypi'`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`
- unique constraint on normalized `(ecosystem, name)`

### `documentation_versions`

One requested package documentation version.

- `id uuid primary key`
- `package_id uuid not null references packages`
- `package_version text not null`
- `status text not null`
- timestamps
- unique `(package_id, package_version)`

### `pipeline_runs`

One resumable execution and its configuration identity.

- `id uuid primary key`
- `documentation_version_id uuid not null references documentation_versions`
- `config_hash text not null`
- `status text not null`
- `started_at`, `completed_at`, `created_at`, `updated_at`
- `error_summary text null`

### `sources`

Confirmed official documentation endpoints.

- `id uuid primary key`
- `documentation_version_id uuid not null`
- `source_type text not null`
- `url text not null`
- `canonical_url text not null`
- `confirmation_status text not null`
- `confirmed_by text null`
- `confirmed_at timestamptz null`
- timestamps
- unique `(documentation_version_id, canonical_url)`

### `source_documents`

Append-only fetched page revisions.

- `id uuid primary key`
- `source_id uuid not null`
- `pipeline_run_id uuid not null`
- `url`, `canonical_url`, `page_title`
- `http_status integer`
- `framework text`
- `raw_content_hash text not null`
- `normalized_content_hash text not null`
- `normalized_markdown text not null`
- `fetch_metadata jsonb not null default '{}'`
- `fetched_at`, `valid_from`, `valid_to`, `created_at`
- `is_current boolean not null`
- `supersedes_id uuid null references source_documents`
- unique current revision per source and canonical URL using a partial index

### `chunks`

Deterministic chunks linked to an exact document revision.

- `id text primary key` — existing deterministic chunk identity
- `source_document_id uuid not null`
- `package_name text not null`
- `package_version text not null`
- `source_url text not null`
- `page_title text not null`
- `header_path jsonb not null`
- `chunk_index integer not null`
- `content text not null`
- `content_hash text not null`
- `character_count integer not null`
- `created_at timestamptz not null default now()`
- unique `(source_document_id, chunk_index)`
- B-tree indexes on package/version, document ID, and content hash

Package and version are intentionally duplicated on chunks for simple, safe
metadata filtering. Foreign-key lineage remains the source of truth.

## Configuration and secrets

Add non-secret database behavior to `config/config.yaml`:

```yaml
database:
  host: "postgres"
  port: 5432
  name: "autodocs"
  user: "autodocs"
  connect_timeout_seconds: 10
```

Keep passwords and full connection URLs in `.env`:

```dotenv
POSTGRES_DB=autodocs
POSTGRES_USER=autodocs
POSTGRES_PASSWORD=change-me
DATABASE_URL=postgresql+psycopg://autodocs:change-me@postgres:5432/autodocs
```

Tests use a separate database name. No real credentials or generated database
files are committed.

## Docker Compose design

The PostgreSQL service must include:

- pinned pgvector image tag;
- environment values from `.env`;
- named volume mounted at the PostgreSQL data directory;
- port mapping configurable for host development;
- health check using `pg_isready`;
- restart policy suitable for development;
- no automatic destructive schema reset.

The dev container should share the Compose network and depend on PostgreSQL
health. Setup applies migrations only after the database is reachable.

## Import transaction

For one package/version run:

1. Normalize the package identity and upsert `packages`.
2. Upsert `documentation_versions`.
3. Insert or resume a `pipeline_runs` record using its run/config identity.
4. Upsert confirmed sources by canonical URL.
5. Compare normalized content hashes with the current document revision.
6. Reuse an unchanged revision; otherwise close it and insert a new revision.
7. Bulk upsert chunks by deterministic ID for the selected document revision.
8. Delete no history. Mark chunks belonging to superseded revisions through
   lineage rather than destructive replacement.
9. Commit all records for a document atomically; roll back that document on
   failure and record the error on the run.

Running the same import twice must leave row counts unchanged except for allowed
run-status timestamps.

## Migration sequence

1. Add database dependencies and typed configuration.
2. Add Compose service and health check.
3. Initialize Alembic and implement migration `0001`.
4. Migration creates `vector`, tables, constraints, partial indexes, and the
   `updated_at` trigger function.
5. Apply upgrade on an empty database.
6. Apply upgrade again to prove operational idempotence.
7. Test downgrade/upgrade only in the disposable integration database.
8. Never auto-generate production migrations without reviewing the SQL diff.

## Testing strategy

Unit tests:

- configuration and URL construction;
- canonical identities and hashes;
- domain-to-persistence mapping;
- repository behavior with mocked session boundaries only where appropriate;
- progress summaries.

Integration tests against real PostgreSQL/pgvector:

- extension and migration availability;
- foreign keys, unique constraints, partial current-revision index;
- transaction rollback;
- importing the same chunk set twice;
- importing changed document content;
- strict package/version isolation;
- container persistence and health.

Do not use SQLite as a substitute for PostgreSQL integration tests because
`jsonb`, partial indexes, triggers, UUID behavior, and pgvector are material to
this design.

## Observability

Every database stage reports:

- pipeline run ID;
- package and version;
- database host/name without credentials;
- packages/versions/sources/documents/chunks inserted or reused;
- failed document count;
- migration revision;
- elapsed time;
- next stage.

Logs retain diagnostic detail while console progress remains concise.

## Security and safety

- redact passwords and connection strings from output;
- use parameterized SQL through SQLAlchemy/Psycopg;
- validate URLs and text sizes before persistence;
- apply a least-privilege application database user;
- reserve migration privileges for setup/migration commands;
- protect reset commands with explicit environment checks and confirmation;
- never mount repository source as the PostgreSQL data directory.

## Acceptance criteria

Stage 4 is complete only when:

1. `docker compose up` starts a healthy pinned PostgreSQL/pgvector service.
2. Alembic upgrades an empty database to the expected revision.
3. The vector extension is enabled, while no embedding dimension is prematurely
   frozen.
4. Existing JSONL chunks import with full package/version/source/document
   lineage.
5. A second identical import creates no duplicate domain records.
6. Changed normalized content creates a new document revision and preserves the
   old revision.
7. Package-version filters cannot return records from another version.
8. Integration tests run against real PostgreSQL and pass in the container.
9. The database survives application-container rebuilds.
10. Backup and restore instructions are tested on disposable data.
11. Console output reports run identity, counts, and the next artifact/location.
12. No Ollama call, embedding vector, similarity index, or semantic retrieval is
    introduced before Stage 5.

## Implementation order and review stops

1. **Review stop A:** dependencies, typed configuration, Compose design.
2. **Review stop B:** schema diagram and migration SQL before applying it.
3. **Review stop C:** repository interfaces and transaction semantics.
4. **Review stop D:** idempotent importer with integration-test evidence.
5. **Stage close:** operational documentation and all acceptance criteria.

Each stop should be a separate commit. Do not combine Stage 5 embedding work
with the final Stage 4 pull request.
